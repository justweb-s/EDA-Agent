# 02 — State Management

## Core Principles

In LangGraph, **state is the communication mechanism** between graph nodes. There are no global variables and no direct dependencies between nodes: each node receives the state, reads it, updates it, and returns a set of updates. LangGraph is responsible for merging updates according to the **annotations** declared on the state `TypedDict`.

This design has an important consequence: every node is a pure function (state in → updates out), which makes the system testable, reproducible, and easy to debug.

---

## Parent Graph State: `EDAState`

`EDAState` is the `TypedDict` that represents an entire analysis session. It is the state the Supervisor reads to make routing decisions, and the state each subgraph receives as input (or a subset of it).

### Fields and responsibilities

#### `messages`: `Annotated[list[AnyMessage], add_messages]`

The complete message history of the session, including system, user, assistant, and tool messages. It uses LangGraph's `add_messages` annotation, which automatically appends new messages instead of overwriting the list.

This field is managed automatically by LangGraph when using `MessagesAnnotation`. Messages are the session's "working memory": older messages are eventually compressed via summarization (see [Memory and Context](./05_memory_and_context.md)).

#### `dataset_context`: `DatasetContext`

`DatasetContext` is an immutable dataclass built during Data Ingestion and never modified during execution. It contains:

- `file_path`: absolute path to the original file
- `file_name`: file name (used in prompts and in the notebook)
- `shape`: tuple `(n_rows, n_columns)`
- `columns`: list of `ColumnInfo` (name, dtype, `n_null`, `n_unique`, `sample_values`, `detected_semantic_type`)
- `memory_usage_mb`: in-memory size
- `preview_markdown`: first 5 rows formatted as a Markdown table
- `basic_stats`: precomputed descriptive statistics (min, max, mean, median, std for numeric; `value_counts` for categorical)
- `detected_issues`: list of automatically detected issues (high % null columns, inconsistent types, possible duplicates)

`detected_semantic_type` is an automatic classification based on column names and values: `numeric_continuous`, `numeric_discrete`, `categorical_nominal`, `categorical_ordinal`, `datetime`, `text_free`, `boolean`, `id_column`. This classification guides the Planner in selecting the appropriate analyses.

#### `eda_plan`: `list[EDAStep]`

The plan generated by the Planner as a list of `EDAStep`. Each `EDAStep` contains:

- `step_id`: unique identifier (e.g. `"dist_age"`)
- `section`: EDA section (e.g. `"distributions"`, `"correlations"`, `"missing_values"`)
- `title`: human-readable title
- `description`: what this step should do and why
- `analysis_type`: analysis type (`univariate`, `bivariate`, `multivariate`, `data_quality`, `feature_specific`)
- `target_columns`: list of involved columns
- `depends_on`: list of `step_id` values that must be completed first
- `is_mandatory`: if `False`, the step can be skipped after repeated failures
- `priority`: integer that defines ordering when there are no dependencies

The plan is **mutable during execution**: the Critic can add corrective steps, and the Conversation agent can add ad-hoc steps in response to user requests.

#### `current_step_index`: `int`

Pointer to the current step in the plan. The Supervisor reads it to know which step to invoke next.

#### `notebook_cells`: `Annotated[list[NotebookCell], append_cell]`

List of all notebook cells accumulated during execution, in order. Each `NotebookCell` contains:

- `cell_type`: `"code"` or `"markdown"`
- `source`: cell content
- `outputs`: list of captured outputs (text, base64 images, HTML dataframes) — code cells only
- `execution_count`: execution number — code cells only
- `step_id`: reference to the EDA step that generated this cell
- `generated_at`: timestamp

It uses a custom `append_cell` annotation instead of overwriting, so each node can add a cell without reading and rewriting the full list.

#### `execution_history`: `Annotated[list[ExecutionSummary], append_summary]`

Semantic history of the analysis: for each completed step, an `ExecutionSummary` containing:

- `step_id`: step reference
- `findings`: natural-language description of what was found (e.g. "Column `age`: approximately normal distribution, mean 35.2, no outliers beyond 3σ, 0.3% null values")
- `key_statistics`: dict of extracted key numeric statistics
- `charts_produced`: list of generated chart names/descriptions
- `anomalies_found`: list of noteworthy anomalies

This field is the system's **adaptive memory**: any agent writing new code reads `execution_history` to know what has already been discovered and what is worth investigating further.

#### `retry_count`: `int`

Retry counter for the current step. Reset to 0 on step changes. When it reaches the configurable `max_retries`, the Supervisor triggers fallback behavior.

#### `critic_feedback`: `CriticReview | None`

The latest feedback from the Critic subgraph. It contains `quality_score`, `missing_analyses`, `shallow_interpretations`, and `verdict`. If `None`, no review has been produced yet for the current section.

#### `mode`: `Literal["auto", "chat"]`

Session operating mode. Determines whether the Supervisor will enter `WAIT_FOR_USER` after completed sections.

#### `hitl_enabled`: `bool`

Flag controlling whether HITL interrupts are executed at the configured touchpoints. If `False`, all interrupts are skipped and the flow is fully automatic.

#### `session_metadata`: `SessionMetadata`

Immutable session metadata:

- `session_id`: UUID generated at startup
- `started_at`: start timestamp
- `llm_provider`: selected LLM provider
- `llm_model`: selected specific model
- `file_name`: analyzed file name

These metadata are used for LangSmith logging and for recovering interrupted sessions.

#### `final_notebook_path`: `str | None`

Path to the final `.ipynb` produced by the Assembler. `None` until the Assembler completes. Its presence is used by the Supervisor as a termination condition.

## Subgraph States

Each subgraph has private state that **is not visible to the parent graph** during internal execution. Communication happens only via declared input/output contracts.

### `PlannerState`

Input from parent: `dataset_context`, `messages`  
Output to parent: `eda_plan`

Internal Planner state:

- `draft_plan`: plan under construction before validation
- `validation_errors`: plan validation errors (circular dependencies, duplicate steps, etc.)
- `iteration_count`: number of refinement iterations

### `EDALoopState`

Input from parent: `current_step`, `dataset_context`, `execution_history`  
Output to parent: `notebook_cells` (new cells to add), `execution_summary` (step findings)

Internal loop state:

- `generated_code`: code generated by the Coder for the current step
- `execution_result`: raw execution result (stdout, stderr, outputs)
- `observer_verdict`: `success`, `retry`, `fatal_error`
- `retry_messages`: history of errors and previous attempts for the current step
- `local_retry_count`: local retry counter (separate from the parent's)

### `CriticState`

Input from parent: `notebook_cells` (only current section cells), `dataset_context`, `section_name`  
Output to parent: `critic_feedback`

Internal Critic state:

- `cells_analyzed`: cells already analyzed
- `partial_review`: review being constructed

### `ConversationState`

Input from parent: `messages`, `dataset_context`, `eda_plan`, `notebook_cells`  
Output to parent: `messages` (agent response), optional modifications to `eda_plan`

Internal state:

- `user_intent`: intent classification of the user message
- `ad_hoc_code`: optional code generated to answer an ad-hoc question
- `ad_hoc_result`: execution result of ad-hoc code

## Annotations and Reducers

LangGraph requires declaring **how** updates to each state field are merged. This declaration is an annotation expressed via `Annotated[type, reducer_function]`.

### Reducer behaviors used in the system

**`add_messages`** (provided by LangGraph): appends new messages to the existing list. It also handles ID-based deduplication and updates existing messages.

**`append_cell`** (custom): appends a single `NotebookCell` or a list of cells to the existing list. It does not allow overwriting existing cells.

**`append_summary`** (custom): appends an `ExecutionSummary` to the list. It checks that no summary with the same `step_id` already exists.

**`overwrite`** (TypedDict default): for all other fields (indices, flags, metadata), the last written value overwrites the previous one. This is the default behavior when no annotation is specified.

## Checkpointing and Serialization

Every field in `EDAState` must be serializable to JSON/pickle in order to be persisted by the checkpointer. This imposes some constraints:

The dataclasses used (such as `DatasetContext`, `EDAStep`, `NotebookCell`) must be convertible to dictionaries. The project uses Pydantic v2 for this, which provides `.model_dump()` and `.model_validate()`.

Cell outputs that include images are stored as base64 strings in the `outputs` field. This increases state size, but guarantees the final notebook remains complete even after resuming from a checkpoint.

`DatasetContext`—especially `preview_markdown` and `basic_stats`—can be verbose. In production, it may be preferable to store only a reference to the data file and rebuild the context from the source on resume, rather than fully serializing it.

---

## Managing the Context Window in `EDAState`

With many steps and verbose outputs, `execution_history` can grow large. Before passing history to the CODER, a filter is applied that includes only findings from steps in the same EDA section plus a compact summary of steps from previous sections. Full details from previous sections are not removed from state—they remain available for the Critic and the Assembler—but they are not included in the Coder prompt.

This balance ensures the Coder always has relevant context without wasting tokens on information that is not useful for the current step.
