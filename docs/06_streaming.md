# 06 — Streaming

## Why Streaming Is Critical

A full EDA can take several minutes. Without streaming, the user would see a spinner for the entire duration and then, suddenly, the complete notebook. That experience is not acceptable for a professional tool.

With streaming, the user sees the analysis being built in real time: first the setup cell appears, then the distribution cell for the first variable, then the corresponding chart, then the interpretive commentary, and so on. The user immediately understands what the system is doing and can intervene if something goes wrong.

---

## LangGraph Streaming Modes

LangGraph exposes multiple streaming modes that can be enabled simultaneously. The primary method is `graph.astream(input, config, stream_mode=[...])`, which returns an async iterator of events.

### `stream_mode="updates"` — State Updates

Emits an event every time a node completes execution and updates state. The event has the following shape:

```
{
  "node_name": {
    "updated_field_1": value,
    "updated_field_2": value
  }
}
```

In this system, this is the most useful mode for the UI: whenever the Observer approves a step and adds notebook cells, an `updates` event arrives with the new `notebook_cells`. The UI can then render cells as they are produced.

### `stream_mode="messages"` — LLM Tokens

Emits LLM tokens as they are generated, along with metadata about the node that produced them. This enables showing text token-by-token in the UI.

Used for:

- Showing CODER code as it is written
- Showing FINDINGS_WRITER interpretive commentary as it is generated
- Showing Conversation agent responses in real time

### `stream_mode="custom"` — Application Signals

Allows nodes to emit arbitrary events via `StreamWriter`. Used to send domain-specific progress signals that are neither state updates nor LLM tokens.

In this system, nodes emit custom events at these points:

- Start of an EDA step ("starting distribution analysis for `age`")
- Start of code execution ("executing code...")
- Execution result ("code executed successfully")
- Start of a retry ("error: %s — retrying...")
- Step completed ("step completed, found N insights")
- Start of Critic review ("Critic is reviewing the distributions section...")

### `stream_mode="values"` — Full State

Emits the full state after each super-step. Not used in the main UI because it is too verbose (it includes the entire state, not just changes), but useful for debugging and for taking state snapshots.

### `stream_mode="debug"` — Maximum Verbosity

Emits maximum detail for every internal LangGraph event. Used only in development for debugging.

### Combining modes

In production, the SSE stream to the browser uses `["updates", "custom", "messages"]` with `subgraphs=True` to receive events from inside subgraphs as well.

## SSE Event Protocol

The FastAPI SSE endpoint translates LangGraph events into typed SSE messages. Each SSE message has an `event` field (type) and a `data` field (JSON payload).

### Defined event types

**`session_started`**  
Emitted when the session is initialized. Payload: `session_id`, `dataset_name`, `llm_provider`, `llm_model`.

**`plan_generated`**  
Emitted when the Planner completes the plan. Payload: list of `EDAStep` with titles and sections. The UI uses this to build the side progress tracker.

**`step_started`**  
Emitted when the loop starts a new step. Payload: `step_id`, `step_title`, `section`, `step_number`, `total_steps`.

**`code_generating`**  
Emitted when the CODER is generating code (before token streaming). Payload: `step_id`.

**`code_token`**  
Emitted for each token of the code generated by the CODER. Payload: `token`, `step_id`. The UI accumulates these tokens to show code appearing in real time.

**`code_executing`**  
Emitted when the EXECUTOR has received the code and is executing it. Payload: `step_id`.

**`execution_result`**  
Emitted when the EXECUTOR completes execution. Payload: `step_id`, `success: bool`, `has_output: bool`.

**`step_retry`**  
Emitted when the Observer decides a retry. Payload: `step_id`, `retry_number`, `error_summary`.

**`cell_added`**  
Emitted when a cell is added to the notebook. Payload: `cell_type` (`code` or `markdown`), `content`, `step_id`, `outputs` (for code cells). This is the most important event for notebook preview in the UI.

**`step_completed`**  
Emitted when a step completes successfully. Payload: `step_id`, `findings_summary`.

**`step_failed`**  
Emitted when a step fails permanently (max retries reached). Payload: `step_id`, `error_summary`.

**`section_completed`**  
Emitted when all steps in a section have completed. Payload: `section_name`, `n_steps_completed`, `n_steps_failed`.

**`critic_reviewing`**  
Emitted when the Critic is reviewing a section. Payload: `section_name`.

**`critic_review_completed`**  
Emitted when the Critic completes a review. Payload: `section_name`, `quality_score`, `verdict`.

**`hitl_interrupt`**  
Emitted when the graph pauses due to a HITL interrupt. Payload: `interrupt_type`, `data` (data to show the user), `available_actions`. The UI uses this to render the approval/modification panel.

**`analysis_completed`**  
Emitted when the full analysis is completed and the notebook is ready. Payload: `notebook_path`, `n_cells`, `n_sections`, `total_duration_seconds`.

**`error`**  
Emitted when an unhandled error occurs. Payload: `error_type`, `error_message`, `recoverable: bool`.

## Backend Implementation

### FastAPI SSE endpoint

`GET /sessions/{session_id}/stream` is an async SSE endpoint. It uses an `async generator` that wraps LangGraph's `astream()` and translates each LangGraph event into the appropriate SSE format.

The mapping from LangGraph events to SSE events is handled by an `EventTranslator`—a dedicated class encapsulating all transformation logic. This keeps the endpoint clean and makes the mapping testable in isolation.

### Disconnect handling

If the SSE client disconnects (e.g., the user closes the browser), the server detects it via Python's async-generator cancellation. The LangGraph run continues in the background (because the session is persisted via checkpointing), but the server stops sending events.

When the client reconnects (e.g., page refresh), it can fetch the current session state via `GET /sessions/{session_id}` and resume streaming from where it left off.

### Backpressure

If the client is slow to consume SSE events (e.g., slow connection), events accumulate in an async queue. A maximum queue size is configured (default: 100 events). When the queue is full, new events are dropped (except high-priority events such as `hitl_interrupt` and `error`).

## Streaming UX Considerations

### Notebook preview

The UI maintains a local representation of the notebook being built, updated on each `cell_added` event. This allows showing the progressively built notebook rather than only a textual operation log.

### Progress indicators

The combination of `step_started` / `step_completed` / `step_failed` events allows the UI to show an accurate progress indicator: "Step 7 of 15: Correlation analysis".

### Retry feedback

When a `step_retry` event arrives, the UI temporarily shows a "retry #N" indicator on the latest step. This provides transparency without being intrusive.

### Code streaming vs final output

Token-by-token code streaming (`code_token`) is visually interesting but optional. The UI allows enabling/disabling it. When disabled, code appears in the notebook only when the step completes (via `cell_added`), producing a cleaner UX.
